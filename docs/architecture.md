# Архитектура приложения

## 1. Анализ требований

Приложение объединяет три независимых сценария, но они имеют много общего. Ниже выделены требования, которые влияют на архитектуру.

### Задание 1. Внутренняя сортировка

- Три самостоятельно реализованных алгоритма: Odd-Even Sort, Tournament Sort и Gnome Sort.
- Ввод массива: генерация, ручной ввод, размер, диапазон значений, сброс.
- Комбинированная визуализация: столбцы, таблица, журнал.
- Пошаговое управление: запуск, пауза, продолжение, ручной шаг, остановка, сброс, скорость.
- Пояснения текущей операции простым языком.
- Информационная карточка алгоритма.
- Итоговая статистика: исходный/отсортированный массив, сравнения, перестановки/перемещения, операции, время.
- Отдельное наглядное турнирное дерево для Tournament Sort.
- Отображение текущей позиции для Gnome Sort.

### Задание 2. Внешняя сортировка

- Natural Merge Sort и External Merge Sort, работающие с файлами и временными сериями.
- Встроенная таблица стран: название, континент, столица, площадь, население.
- Загрузка пользовательского CSV с произвольным числом столбцов.
- Выбор ключа, направления, типа значения, фильтра по континенту.
- Пошаговая визуализация поиска серий и слияния.
- Журнал чтения/записи/сравнений.
- Сохранение полных записей в CSV, путь к результату, открытие папки.
- Стабильность сортировки и корректная очистка временных файлов.

### Задание 3. Текст и эксперименты

- Два самостоятельно реализованных алгоритма: QuickSort и Radix Sort.
- Загрузка TXT или воспроизводимая генерация текста.
- Единые правила нормализации и сравнения для обоих алгоритмов.
- Подсчёт частот, поиск, общая и уникальная статистика.
- Эксперименты на 100/500/1000/2000/5000+ словах, несколько замеров, медиана.
- Таблица результатов и график с двумя сериями.

### Общие требования

- Единый интерфейс, светлая тема, русский язык.
- Отсутствие зависаний, отмена через `CancellationToken`.
- Обработка ошибок ввода, файлов, повторного запуска, закрытия приложения.
- Автоматические тесты алгоритмов независимо от UI.
- Актуальный GitHub-репозиторий.

## 2. Ключевые архитектурные решения

### 2.1. Три проекта

```text
SortingLab.Core   — чистый C#: алгоритмы, модели, события, CSV, файлы, текст, бенчмарки
SortingLab.App    — Avalonia UI: представления, ViewModel, проигрывание шагов, рисование
SortingLab.Tests  — xUnit: тесты ядра без Avalonia
```

**Почему так.** Алгоритмы не должны зависеть от Avalonia. Ядро можно тестировать обычными модульными тестами, запускать в фоне и переиспользовать. UI зависит от ядра, но не наоборот. Это даёт соблюдение SRP и DIP в разумных для учебного проекта пределах.

`SortingLab.Core` не ссылается на Avalonia. `SortingLab.App` не содержит реализаций алгоритмов. `SortingLab.Tests` ссылается только на Core.

### 2.2. Слои внутри Core

| Слой | Ответственность | Примеры |
|---|---|---|
| Модели | Неизменяемые данные | `ArraySortStep`, `ExternalSortStep`, `OperationStatistics`, `CsvTable` |
| Исполнение | Контекст шага, счётчики, поток событий | `ArraySortContext`, `StepChannel<T>`, `CollectingStepSink<T>` |
| Алгоритмы | Только логика сортировки | `OddEvenSort`, `TournamentSort`, `GnomeSort`, `NaturalMergeSorter`, `ExternalMergeSorter`, `QuickSort`, `RadixSort` |
| Данные | CSV, временные файлы, текст | `CsvTableReader`, `CsvTableWriter`, `TextTokenizer`, `TextGenerator` |
| Эксперименты | Замеры без UI | `BenchmarkRunner`, `WordFrequencyAnalyzer` |

### 2.3. Слои внутри App

| Слой | Ответственность |
|---|---|
| Views | Разметка Avalonia и визуальные контролы |
| ViewModels | Состояние экрана, команды, валидация, подготовка данных для визуализации |
| Services | Диалоги, проигрывание шагов, загрузка встроенного CSV, открытие папки |
| Controls | Самостоятельно рисуемые диаграммы и адаптивный `ResponsiveTwoColumnPanel` |
| Styles | Единая палитра, типографика, стили кнопок, таблиц, карточек |

Двухколоночные разделы используют `ResponsiveTwoColumnPanel`: при недостаточной ширине основная и боковая панели складываются вертикально. Это устраняет горизонтальное переполнение при изменении размеров окна. Приложение также подбирает начальный размер окна по рабочей области экрана.

## 3. Взаимодействие ядра и интерфейса

```text
ViewModel
   │ 1. создаёт запрос и StepChannel<TStep>
   ▼
Фоновый Task ──► Алгоритм ──► ArraySortContext/ExternalSortContext
                                   │ счётчики + событие шага
                                   ▼
                             IStepSink<TStep> (unbounded channel)
                                   │
                                   ▼
PlaybackViewModel ◄── IAsyncEnumerable<TStep> ── UI-поток
   │ 2. пауза / шаг / скорость / отмена
   │ 3. применяет шаг к визуальному состоянию
   ▼
BarChart / DataGrid / Journal / Explanation / Stats
```

Алгоритм не знает о UI. Он получает `IStepSink<TStep>` и CancellationToken. Каждый шаг содержит:

- номер;
- тип операции;
- заголовок и понятное пояснение;
- индексы и значения участников;
- снимок статистики на момент шага;
- при необходимости — снимок массива, турнирного дерева, серий или файловых операций.

Событийная модель расширена без изменения интерфейса проигрывателя: для Gnome Sort добавлено событие текущей позиции. Внешние алгоритмы используют существующие `ExternalSortStep` и события серий/слияния.

### 3.1. Почему события, а не возврат готового массива

Возврат только результата не позволяет показать процесс. События отделяют вычисление от отображения, позволяют вести журнал, собирать статистику и добавлять новые алгоритмы без изменения UI-контракта.

### 3.2. Почему канал событий

`StepChannel<T>` — обёртка над `System.Threading.Channels.Channel`:

- алгоритм пишет шаги без блокировки UI;
- UI читает их через `IAsyncEnumerable`;
- при завершении канал закрывается;
- исключение алгоритма передаётся в UI, а не теряется;
- отмена прекращает и вычисление, и чтение.

Канал **неограниченный**, но размеры входных данных для демонстрации ограничены (массив до 200 элементов, таблица стран — 195 записей). Это осознанный компромисс: алгоритм не ждёт медленный UI, время выполнения не искажается паузой, а объём событий предсказуем. Для внешней сортировки события агрегированы: одна запись журнала на сравнение/запись, а не на каждый байт файла.

Для тестов используется `CollectingStepSink<T>` — синхронный сборщик без каналов и UI.

### 3.3. Почему не сохраняются полные снимки на каждом шаге

Снимок всего массива после каждой операции быстро увеличивает память. Вместо этого:

- начальный снимок передаётся один раз;
- сравнение/перестановка содержат только индексы и значения;
- UI поддерживает собственное текущее состояние и применяет операции;
- полный снимок передаётся в начале и в конце, а также в турнирном дереве (дерево мало: ≤ 2n узлов);
- для внешней сортировки передаются метаданные серий и файловых операций, а не содержимое файлов целиком.

Такой баланс даёт пошаговость без хранения тысяч копий массива.

## 4. Пошаговое воспроизведение

`PlaybackViewModel` — общий компонент для заданий 1 и 2. Он не знает конкретный алгоритм и работает с базовым `DemoStep`.

### 4.1. Состояния

```text
Idle ──Start──► Running ──Pause──► Paused
                  │  ▲                │
                  │  └────Resume──────┘
                  │  └────Step────────┘ (один шаг, снова Paused)
                  ├──Stop──► Cancelled
                  ├──Complete──► Completed
                  └──Error──► Faulted
Idle/Completed/Cancelled/Faulted ──Reset──► Idle
```

Команды кнопок привязаны к `CanExecute` через CommunityToolkit.Mvvm. Нельзя запустить второй экземпляр демонстрации в том же разделе: `Start` недоступен, пока состояние `Running`/`Paused`.

### 4.2. Ручной шаг

- `Step` при `Idle` запускает сессию в режиме паузы и применяет начальное состояние.
- `Step` при `Paused` разрешает ровно один шаг; после него цикл снова ждёт.
- `Pause` не сбрасывает вычисления; алгоритм может продолжить работу в фоне, но отображение стоит на месте.
- `Resume` снимает паузу и продолжает с текущей задержкой.
- `Stop` отменяет `CancellationToken`, что останавливает и алгоритм, и чтение канала.
- `Reset` останавливает сессию, очищает журнал и возвращает исходные данные для повторного запуска.

Задержка читается перед каждым шагом, поэтому изменение ползунка действует сразу.

### 4.3. Потокобезопасность

- Алгоритм работает в `Task.Run`.
- Запись в канал потокобезопасна.
- Чтение и применение шагов выполняются в UI-контексте.
- `CancellationTokenSource` создаётся на сессию. `Stop`/`Reset`/закрытие окна отменяют его.
- Исключения фонового производителя передаются через канал и переводят UI в состояние ошибки с понятным сообщением.

## 5. Статистика

`OperationStatistics` — неизменяемый снимок:

```text
Comparisons   — сравнения ключей
Swaps         — обмены элементов массива
Moves         — перемещения/записи в результирующий массив
Writes        — записи во временный файл (внешняя сортировка)
Reads         — чтения записей (внешняя сортировка)
TotalOperations — суммарное число операций
ElapsedMilliseconds — время работы алгоритма
```

Счётчики увеличиваются в контексте выполнения, а не восстанавливаются из журнала. Поэтому они корректны и для тестов, и для UI, и при отмене.

Время измеряется `Stopwatch` внутри ядра. В бенчмарках заданий 3 используется отдельный `Stopwatch`, который охватывает только вызов алгоритма: генерация, нормализация, копирование массива и отрисовка не входят.

## 6. Фоновые операции и отмена

- Все длительные операции (сортировка, внешняя сортировка, бенчмарки) выполняются в фоне.
- UI не блокируется: чтение событий идёт асинхронно.
- Отмена передаётся во все циклы алгоритмов и в файловые операции.
- Внешний сортировщик создаёт временный каталог с уникальным именем и удаляет его в `finally` как при успехе, так и при отмене/ошибке.
- При старте приложение очищает устаревшие временные каталоги прошлых сессий.
- Закрытие окна отменяет активные сессии; критические файловые операции завершаются очисткой.

## 7. Внешняя сортировка: архитектура

`NaturalMergeSorter` и `ExternalMergeSorter` получают:

- исходный CSV-файл (встроенный или пользовательский, уже отфильтрованный);
- индекс ключевого столбца;
- тип ключа;
- направление;
- каталог для временных файлов.

Процесс:

1. Записи исходной таблицы сериализуются в рабочий файл (JSON Lines) — исходный CSV не изменяется.
2. Natural Merge Sort находит максимальные неубывающие серии по ключу; External Merge Sort принудительно создаёт серии по одному элементу.
3. Каждая серия выгружается в отдельный временный файл.
4. Серии попарно сливаются в новые файлы; входные файлы удаляются после успешного слияния.
5. Проходы повторяются, пока не останется одна серия.
6. Финальный файл переписывается в CSV пользователя со всеми исходными столбцами.

Оба алгоритма используют один файловый конвейер слияния и различаются только построением начальных серий. Стабильность обеспечивается правилом: при равных ключах выбирается запись из левой серии.

События отражают:

- поиск серии (диапазон, количество, ключи);
- начало слияния;
- сравнение двух записей;
- выбор и запись записи;
- завершение слияния;
- завершение прохода;
- итог и путь к результату.

## 8. Текст и эксперименты

`TextTokenizer` — единый вход для QuickSort и Radix Sort:

- Unicode-нормализация Form C;
- приведение к нижнему регистру `ToLowerInvariant`;
- выделение последовательностей букв и цифр;
- поддержка кириллицы и латиницы;
- одинаковые правила для обоих алгоритмов.

`WordFrequencyAnalyzer` проходит по уже отсортированному массиву один раз и группирует одинаковые слова. Используется в UI для таблицы частот.

`BenchmarkRunner`:

- генерирует данные один раз до запуска `Stopwatch`;
- для каждого размера создаёт независимые копии массива;
- выполняет прогрев;
- делает несколько замеров и берёт медиану;
- не измеряет UI, генерацию и копирование;
- возвращает строки таблицы и точки графика.

## 10. Расширяемость

Новый алгоритм внутренней сортировки:

1. Реализует `IArraySortAlgorithm`.
2. Возвращает `AlgorithmDescriptor` (название, идея, сложность, память, особенности).
3. Пишет шаги через `ArraySortContext`.
4. Регистрируется в списке алгоритмов ViewModel.

UI не меняется. Аналогично новый внешний алгоритм реализует `IExternalSortAlgorithm` (или отдельный сервис) и использует тот же канал событий. Новый текстовый алгоритм реализует `ITextSortAlgorithm` с общим `StringComparer`.

## 12. Обработка ошибок

- Валидация ввода во ViewModel до запуска; сообщения на русском.
- Пустые массивы и тексты обрабатываются алгоритмами и UI как корректный граничный случай.
- Ошибки CSV: понятное сообщение с номером строки, предложение проверить разделитель/заголовки.
- Ошибки файлов: перехват `IOException`, `UnauthorizedAccessException`, отображение в панели ошибки.
- Отмена: отдельное состояние «Отменено», без сообщения об ошибке.
- Повторный запуск: команда `Start` недоступна во время работы, после завершения/сброса доступна.
- Закрытие приложения: отмена токенов, очистка временных каталогов.

## 13. Тестирование

- Юнит-тесты алгоритмов на граничные случаи, дубликаты, отрицательные значения, большие массивы, Unicode.
- Проверка статистики и того, что алгоритмы не используют `Array.Sort`/`List.Sort` для результата.
- Тесты CSV: разделители, кавычки, пустые значения, произвольное число столбцов.
- Тесты внешней сортировки: стабильность, сохранение всех полей, реальные временные файлы, отмена.
- Тесты текста: нормализация, пунктуация, регистр, кириллица/латиница, частоты, совпадение QuickSort и Radix Sort.
- UI проверяется сборкой, запуском и ручным сценарием; ключевая логика вынесена из Views.
- `PlaybackViewModel` дополнительно покрыт тестами: запуск до завершения, ручной шаг, пауза/продолжение, ошибка, сброс и журнал.

Актуальный набор — 97 тестов; все проходят в конфигурации Release.

## 14. Обоснование отказа от альтернатив

- **Один монолитный проект** — быстрее начать, но алгоритмы смешались бы с UI, тесты зависели бы от Avalonia, а задания дублировали бы код.
- **ReactiveUI** — мощный, но для данного объёма достаточно CommunityToolkit.Mvvm; меньше неявной магии.
- **Сторонняя библиотека графиков** — добавила бы тяжёлую зависимость и ограничила бы оформление. Небольшие контролы на `DrawingContext` проще стилизовать и тестировать визуально.
- **Сохранение всех снимков массива** — неоправданный расход памяти; событийная модель с применением операций достаточна.
- **Полная загрузка внешней сортировки в память** — нарушила бы смысл задания; сортировщик работает с файлами, хотя UI держит загруженную таблицу для отображения.
